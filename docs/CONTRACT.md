# HTTP Contract — client ↔ proxy

**Status: frozen for Phase 1.** Orchestrator-owned. If you need a change, stop and
report it; do not edit this file or `shared/types.ts`. Both sides of this boundary
are being built in parallel, and a unilateral change silently breaks the other worker.

All types referenced below live in [`shared/types.ts`](../shared/types.ts). Import them
via `@shared/types` — never redeclare them locally.

---

## Data source

The proxy serves this contract from a **`MarketEngine`** implementation, selected by
`DATA_PROVIDER` in `server/env.ts`:

- **`synthetic`** (default, no credentials) — a deterministic generated market, per
  [`server/market/types.ts`](../server/market/types.ts).
- **`massive`** — the real massive.com API. Not implemented yet; the upstream paths
  and shapes documented below are the specification for whoever writes it.

The contract below is **identical either way**. If any client code can tell which
provider is active, the seam has leaked.

## Global rules

**Base path.** All endpoints are under `/api`. The client calls them same-origin;
Vite forwards `/api/*` to the proxy in dev. The client never constructs an upstream
massive.com URL and never holds the API key.

**Envelope.** Every response — success or failure — is an `ApiResult<T>`:

```jsonc
{ "ok": true,  "data": { /* ... */ } }
{ "ok": false, "error": { "code": "RATE_LIMITED", "message": "…", "retryAfterSeconds": 12 } }
```

HTTP status still reflects the outcome (200 / 400 / 404 / 429 / 502 / 504 / 500), so
callers can branch on either. The client switches on `error.code`, **never** on
`error.message` text.

**Time is Unix seconds, UTC, in every field of every payload.** Upstream returns
milliseconds; `server/massive/` divides by 1000 exactly once. No route handler and
no client module ever sees milliseconds. A `/ 1000` anywhere outside `server/massive/`
is a bug.

**Error messages are user-safe.** Never include the API key, a raw upstream URL, or
an upstream stack trace. Use `redact()` from `server/env.ts` on anything derived from
an upstream response before it reaches a log or a message.

**Status code → code mapping.**

| Upstream / condition | HTTP | `error.code` |
|---|---|---|
| Invalid caller params (zod failure) | 400 | `BAD_REQUEST` |
| Symbol not found upstream | 404 | `UNKNOWN_SYMBOL` |
| Valid request, genuinely empty result | 200 | — (`ok: true`, empty array) |
| Upstream 401/403 | 500 | `UNAUTHORIZED` |
| Upstream 429 | 429 | `RATE_LIMITED` |
| Upstream 5xx or unparseable body | 502 | `UPSTREAM_ERROR` |
| Upstream timeout | 504 | `UPSTREAM_TIMEOUT` |
| Anything else | 500 | `INTERNAL` |

Note: an empty result is **success with an empty array**, not `NO_DATA`. Reserve the
`NO_DATA` code for the case where upstream explicitly reports no data for an otherwise
valid symbol and range.

## `GET /api/capabilities`

What the configured provider can actually do, so the client can present only what it
can deliver.

**Success:** `ApiResult<{ timeframes: Timeframe[]; delayed: boolean; provider: string }>`

- `timeframes` — the subset of `TIMEFRAMES` this provider serves. The client disables
  the rest rather than offering a control that will fail.
- `delayed` — whether this provider's data is delayed. The UI does not badge it (user decision, 2026-10-11).
- `provider` — the active provider's name. **Never** any part of a key. The UI badges the data
  as synthetic when it is `synthetic` or `mock` (src/data/capabilities.ts).

Requesting an unsupported timeframe from `/api/bars` is `UNAUTHORIZED` (500), which this
contract has always defined as covering a key that "lacks the plan tier for this data".
That is the backstop for a stale client, not the intended path.

## `GET /api/bars`

Historical OHLCV. The core endpoint.

| Param | Type | Required | Notes |
|---|---|---|---|
| `symbol` | string | yes | 1–16 chars. Pass through **verbatim**; the engine resolves case-insensitively and the response echoes the canonical form. |
| `timeframe` | `Timeframe` | yes | One of `1m 5m 15m 1h 1D 1W`. Anything else → `BAD_REQUEST`. |
| `from` | int | yes | Unix **seconds**, inclusive. Values below 0 are **clamped to 0**, not rejected. |
| `to` | int | yes | Unix **seconds**, inclusive. Must be `>= from`. |
| `adjusted` | bool | no | Default `true`. |

**Success:** `ApiResult<BarsResponse>`.

### Timeframe mapping

The proxy owns this table. The client never sends `multiplier`/`timespan`.

| `timeframe` | `multiplier` | `timespan` |
|---|---|---|
| `1m` | 1 | `minute` |
| `5m` | 5 | `minute` |
| `15m` | 15 | `minute` |
| `1h` | 1 | `hour` |
| `1D` | 1 | `day` |
| `1W` | 1 | `week` |

Upstream: `GET /v2/aggs/ticker/{symbol}/range/{multiplier}/{timespan}/{from}/{to}`
with `adjusted` and `limit=50000`. See guarantee 4 below on sort order — `sort=asc`
with a page cap silently drops the newest bars, which is the wrong end to lose.

### Guarantees the proxy must uphold

1. **Ascending, strictly increasing `time`, no duplicates.** Sort and de-duplicate
   after merging pages; do not trust upstream ordering across page boundaries.
2. **Milliseconds converted to seconds.** Once, in `server/massive/`.
3. **`vwap` and `transactions` are `number | null`.** Upstream `vw`/`n` are sometimes
   absent. Absent becomes `null`, never `0` — a zero VWAP is a plausible-looking lie.
4. **Truncation keeps the NEWEST bars, never the oldest.** When a request covers more
   bars than the proxy will return, it returns **the most recent `limit` bars in range**
   and sets `truncated: true`. The partial edge is therefore the **oldest** returned
   bar, and the client continues backwards from there — which is exactly how the chart
   lazy-loads history as the user pans left.

   This matters because the naive implementation does the opposite. Fetching upstream
   with `sort=asc` from `from` and stopping at a page cap drops the *newest* bars,
   which means a chart asking for a wide range opens on stale history with a gap
   where the present should be. A real-upstream implementation must therefore either
   fetch with `sort=desc` or fetch ascending and keep the tail.

   For a real upstream, follow `next_url` to collect pages (upstream's default `limit`
   is 5,000 and silently truncates). `next_url` arrives **without** the API key —
   re-attach it before following.
5. **Range filtering is inclusive** on both ends after conversion to seconds.

5a. **No bars in the future, and no future data inside a present bar.** The proxy
   clamps `to` to the current time before calling the engine, and never returns a bar
   whose `time` is after now. The newest bar may straddle now, and when it does it must
   reflect **only elapsed time**: its open, high, low, close, volume and transactions
   must be computed from the part of the bucket that has actually happened. A bucket
   that has begun but in which nothing has traded yet is dropped, not returned empty.

   The second clause is the one that matters, and the first version of this guarantee
   omitted it. Clamping `to` is not sufficient on its own. A bar is stamped with its
   *open*, so a clockless engine hands back today's 1D bar — timestamped 09:30, and
   therefore passing any "no bar after now" check — carrying the 16:00 close and the
   full day's volume. Midweek, the weekly bar carries Thursday and Friday. The
   timestamp looks innocent while the OHLC leaks prices that have not happened, which
   makes this strictly worse than returning an obviously future-dated bar.

   **The forming bar ends at the last completed minute.** A minute that is still in
   progress is excluded, not included whole. The engine's atom is one minute, so
   including a partially-elapsed minute means including the rest of that minute — the
   same future-data leak this guarantee exists to prevent, just one bucket smaller.
   This also makes the chart's newest close agree with `/api/snapshot`, which already
   uses completed minutes only; the two sit side by side in the header-plus-chart
   layout, and disagreeing there is a visible contradiction.

   Rebuilding the forming bar from 1-minute bars is exact rather than approximate
   because engine invariant 2 guarantees every bucket is the exact aggregate of its
   minutes. That is a dependency on the engine seam, not an implementation detail of
   one provider: any future provider must offer the same guarantee, or state how the
   forming bar is to be built instead.

   This was missing from the first version of this contract, and the omission was
   load-bearing: a deterministic engine has no clock by design — its whole contract is
   that a bar is identical regardless of what else was requested — so it will happily
   generate 2027 for you. Asking for a wide range therefore returned a year of
   fabricated future candles. Neither the engine nor the route was wrong; the spec
   simply never said. The clamp belongs here, at the HTTP layer, because it is the
   only layer that is allowed to know what time it is.
6. **`cached`** reports whether this response came from the proxy's LRU. Diagnostics only;
   the client must behave identically either way.

### Request bounds

A single request must not be able to consume unbounded CPU or memory. The engine is
**synchronous**, so one oversized request blocks the event loop and the server answers
nothing else meanwhile — including `/api/health`.

- Cap the number of bars any one request may return, per timeframe, independent of the
  caller's range. Exceeding it is not an error: return the newest bars within the cap
  and set `truncated: true`, exactly as guarantee 4 describes.
- A request whose range is wider than the cap allows must not be handed to the engine
  whole. Narrow the range first.

### Caching

LRU keyed on `symbol|timeframe|from|to|adjusted`, with `to` replaced by a `'now'`
sentinel whenever the caller is asking for data up to the present, so that requests
differing only in a future or near-present `to` share one entry.

Policy: intraday timeframes short TTL (~60s), daily/weekly longer (~10min).

**Bound the cache by total bars, not by entry count.** An earlier version of this
section said "a 50,000-bar response is a few MB and a few hundred entries is plenty".
That was wrong by about two orders of magnitude: 200 entries of 50,000 live `Bar`
objects measures at roughly **1.5 GB** of heap, because the cost is per-object
overhead, not JSON bytes. Size the cache by summed bar count with a hard ceiling, and
bound the work per request as well — see "Request bounds" below.

## `GET /api/indicator` — **ORACLE / DEBUG ONLY**

> **Do not call this from application code.** Runtime indicators are computed
> client-side in `src/indicators/` from bars already in hand. This endpoint exists
> solely so Worker C's unit tests can compare local math against upstream's own
> SMA/EMA/MACD/RSI output as ground truth.

Reasons runtime computation wins: no API quota burned per indicator, parameter
changes recompute instantly, and indicators keep working while panning through
cached bars.

| Param | Type | Required | Notes |
|---|---|---|---|
| `symbol` | string | yes | |
| `timeframe` | `Timeframe` | yes | |
| `kind` | `IndicatorKind` | yes | `sma` \| `ema` \| `rsi` \| `macd` \| `volume` |
| `from`, `to` | int | yes | Unix seconds |
| `period` | int | for `sma`/`ema`/`rsi`/`volume` | For `volume`, the moving-average length |
| `fastPeriod`, `slowPeriod`, `signalPeriod` | int | for `macd` | |

**Success:** `ApiResult<IndicatorSeries>`.

For `macd`, upstream returns value/signal/histogram; map them to `lines` with keys
`macd`, `signal`, `histogram` in that order. For `volume`, two lines: `volume` (each
bar's volume) and `ma` (the SMA of the volume over `period` bars). For the others, a
single line with key `value`.

`vpvr` (visible-range volume profile) is a valid `IndicatorKind` for layouts, but this
endpoint does not serve it: its profile depends on the chart's visible range, so the
client computes it at draw time.

`liquidity` (zones and sweeps, docs/LIQUIDITY_PLAN.md) is a valid `IndicatorKind` for layouts,
but this endpoint does not serve it: its output is drawings, not lines. `LiquidityParams`:
`lookback` 2–100 (default 10), `zoneMode` `wick`|`range` (default `wick`), `sweepMode`
`wicks`|`retests`|`both` (default `wicks`), `minTouches` 0–100 (default 0), `maxAge` 10–5000
(default 300), `sweepExtend` 1–500 (default 20). All numbers are integers. The workspace store
refuses any other value with `BAD_REQUEST`.

`confluence` (turn and breakdown trigger levels, docs/CONFLUENCE_PLAN.md) is a valid
`IndicatorKind` for layouts, but this endpoint does not serve it: its output is drawings, not
lines. `ConfluenceParams`: `mode` `turn`|`breakdown` (default `turn`); integers `swingLookback`
20–1000 (250), `pivotLeft` and `pivotRight` 1–25 (5), `pivotMaxAge` 10–5000 (250),
`turnMinConfluence` and `breakdownMinConfluence` 1–20 (1 and 3), `volumeLength` 1–500 (10);
decimals `tolerancePct` 0.05–5 (0.75), `bandWidthMult` 0–20 (0), `turnMinDistancePct` and
`breakdownMinDistancePct` 0–20 (0 and 0.5), `volumeMult` 1–10 (1.5), `closeQuality` 0.1–1
(0.5); `sources` `both`|`fibs`|`mas`|`none` (`both`); `latch` `off`|`on` (`off`); `latchTime`
integer Unix seconds 0–4102444800 (0, no date). The workspace store refuses any other value
with `BAD_REQUEST`.

Upstream: `/rest/stocks/technical-indicators/{sma,ema,macd,rsi}`.

## Client-side expectations

- `src/data/` exposes a `DataSource` interface over these endpoints. Phase 1 has
  exactly one implementation (HTTP-over-`fetch`); a WebSocket implementation lands
  later behind the same interface, so **no component may call `fetch` directly**.
- During Phase 1 the client runs against MSW handlers in `mocks/` that serve the
  Phase 0 fixtures. Swapping MSW for the real proxy happens in Phase 2 and must
  require **no component changes** — if it does, the abstraction leaked.
- Every endpoint can fail. Loading, empty, and error states are part of the
  Phase 1 deliverable, not Phase 4 polish.

## `GET /api/quotes?symbols=AAPL,MSFT,...` — batch quotes for the watchlist

| Param | Rule |
|---|---|
| `symbols` | Comma-separated, 1–`MAX_QUOTE_SYMBOLS` (50) entries, each 1–16 chars. Empty or too many → `BAD_REQUEST`. |

**Success:** `ApiResult<QuotesResponse>` — `{ quotes, missing, failed }`.

- **Partial success is normal.** An unknown symbol goes to `missing`; a resolved symbol
  whose fetch failed goes to `failed`. Neither fails the request. The request fails as
  a whole only for bad params, or when EVERY symbol failed (then use the first error's code).
- `quotes` is in request order, with canonical symbols, de-duplicated case-insensitively.
- **The proxy fans out to `engine.getSnapshot` per symbol** with a concurrency limit of 5,
  through a shared quote cache (TTL 15 s, successes only). Two watchlists that share a
  symbol fetch it once.
- **FMP trap, measured:** `/stable/quote?symbol=AAPL,MSFT,NVDA` answers HTTP 200 with an
  EMPTY array. It looks like success and returns nothing. `batch-quote` and
  `batch-quote-short` are HTTP 402 on Starter. There is no batch endpoint: fan out.
- **Rate budget (FMP Starter, 300 calls/min).** A full 50-symbol list polled every 30 s
  costs at most 100 calls/min before the cache helps. The client therefore polls every
  30 s, and only while the page is visible (`document.visibilityState === 'visible'`).

## Workspace — named layouts and watchlists

Stored server-side in one JSON file (`WORKSPACE_FILE`, default `data/workspace.json`).
Single user, no authentication: the server binds `127.0.0.1` only.
Invariants for the store are in `server/workspace/types.ts`.

| Method & path | Body | Success |
|---|---|---|
| `GET /api/workspace` | — | `Workspace` |
| `GET /api/layouts` | — | `{ layouts: ChartLayout[], activeLayoutId }` |
| `POST /api/layouts` | `CreateLayoutBody` | `ChartLayout` (201) |
| `PUT /api/layouts/:id` | `UpdateLayoutBody` | `ChartLayout` |
| `DELETE /api/layouts/:id` | — | `Workspace` |
| `GET /api/watchlists` | — | `{ watchlists: Watchlist[], activeWatchlistId }` |
| `POST /api/watchlists` | `CreateWatchlistBody` | `Watchlist` (201) |
| `PUT /api/watchlists/:id` | `UpdateWatchlistBody` | `Watchlist` |
| `DELETE /api/watchlists/:id` | — | `Workspace` |
| `PUT /api/workspace/active` | `SetActiveBody` | `Workspace` |

- Bodies are JSON, validated with zod. Unknown fields → `BAD_REQUEST`.
- **Optimistic concurrency.** `PUT` must carry the `revision` it was based on. A stale
  revision → `CONFLICT` (409). The client then refetches, shows the current state, and
  tells the user. It never retries the same write blindly.
- Unknown id → `NOT_FOUND` (404). Validation failures (names, limits, last layout,
  bad symbol format, invalid indicator params) → `BAD_REQUEST` with a user-safe message.
- The default workspace is created on first read: layout "Main" (AAPL, 1D, candlestick),
  watchlist "Watchlist" (AAPL, MSFT, NVDA, AMZN, GOOGL).
- The MSW mock in `mocks/workspace.ts` implements this table exactly, and tests guard it.
  It is orchestrator-owned: client workers build against it and do not edit it.

| Path | Params | Success |
|---|---|---|

## Alerts

The plan is `docs/ALERTS_PLAN.md`. The types are in `shared/types.ts` (`Alert`, `AlertEvent`,
`AlertCondition`, …). Alerts and events are stored server-side in their own JSON file
(`ALERTS_FILE`, default `data/alerts.json`), not in the workspace file, so checker writes
never change the workspace revision. The server checks the alerts; the client only shows them.

| Method & path | Body | Success |
|---|---|---|
| `GET /api/alerts` | — | `AlertsResponse` (`{ alerts, checkIntervalSeconds }`, newest first) |
| `POST /api/alerts` | `CreateAlertBody` | `Alert` (201) |
| `PUT /api/alerts/:id` | `UpdateAlertBody` | `Alert` |
| `DELETE /api/alerts/:id` | — | `{ id }` |
| `GET /api/alerts/events?since=` | — | `AlertEventsResponse` (newest first; `since` is optional Unix seconds, exclusive) |
| `PUT /api/alerts/events/checked` | `SetCheckedBody` (`{ ids }` with 1–1000 ids, or `{ all: true }`) | `{ unchecked }` |
| `DELETE /api/alerts/events/:id` | — | `{ unchecked }` |
| `GET /api/alerts/stream` | — | `text/event-stream` |

- Bodies are JSON with strict zod schemas (`server/alerts/schemas.ts`). Unknown fields →
  `BAD_REQUEST`. The body is validated BEFORE the id is looked up.
- Semantic checks are `checkAlertCondition` and `checkAlertMessage` in
  `src/alerts/condition.ts`. The dialog, the store and the mock use them.
  - Price: `level` is a positive finite number.
  - Indicator: `kind` is in `ALERT_INDICATOR_KINDS` (sma, ema, rsi, macd); `params` pass
    `checkIndicatorParams`; `line` is in `LINE_KEYS[kind]`; a `line` target is another line
    of the same indicator; a `value` target is finite. A `close` target is only for SMA and
    EMA (`CLOSE_TARGET_KINDS`), because RSI and MACD are not on the price scale. An alert in
    the file that was saved before this rule still loads.
  - `message` is 0–`MAX_ALERT_MESSAGE_LENGTH` (200) characters.
- Symbols use the workspace format and are stored upper case. There is no limit on the
  number of symbols. At most `MAX_ALERTS` (1000) alerts → else `BAD_REQUEST`.
- Defaults on create: `frequency: 'once'`, `expiry: '1M'`, `message: ''`, `status: 'active'`.
- `expiresAt` = `computeExpiresAt(now, expiry)` (`src/alerts/expiry.ts`): weeks add 7 days;
  months and years add calendar months in UTC, and the day clamps to the end of a short month.
  A new `expiry` in a `PUT` counts from the time of the `PUT`.
- **Optimistic concurrency** as for the workspace: `PUT` carries `revision`; stale →
  `CONFLICT` (409). Only user edits raise `revision`. The checker writes `state`, `status`
  (`triggered`, `expired`) and events, and never raises `revision`.
- `PUT` with `status: 'active'` enables a `paused`, `triggered` or `expired` alert again. A
  new `condition` or a status change to `active` resets `state.lastSide`,
  `state.lastDayHigh`, `state.lastDayLow` and `state.lastBarTime`, so the first check after it only records the side and does not fire.
  When `expiresAt` already passed, enabling counts the expiry choice from now. A new
  `expiry` on an `expired` alert also makes it `active`.
- Unknown id → `NOT_FOUND` (404).
- Events keep a copy of the condition and the message, so they stay readable after the
  alert is deleted. The log keeps the newest `MAX_ALERT_EVENTS` (1000) events.
- `firedAt` is the time of the check. An indicator event also has `barTime`: the open time
  of the closed bar that crossed. A price event has no `barTime`.
- The edit dialog sends only the fields that changed, so an edit of the message does not
  reset the side or the expiry time.
- **Stream.** Each message is an SSE event whose name is the `type` of an
  `AlertStreamMessage`, and whose `data` is that message as JSON:
  - `fired`: an alert fired. Carries the event and the alert after the change.
  - `checked`: the checked state or the event log changed. Carries the new `unchecked` count,
    and `checkedIds` (the ids marked as checked, or `'all'`) or `deletedId` (a deleted event).
    The client applies the change and does not load the log again. A `checked` message with
    neither field means: load the events again.
  - `alerts`: alerts were created, edited, deleted, or changed status. Load the list again.
  - `budget`: the checker used all its calls for this minute while checks were due. Carries
    `budgetPerMinute` and `waitingSymbols`. The client shows a warning that the user can
    dismiss. The server sends it once per shortage (a shortage after a full minute with
    none is a new one), and at most `ALERT_BUDGET_WARNINGS` (3) times per server run.

  A client that reconnects loads the events it missed with `GET /api/alerts/events?since=`.
- **The checker** (`server/alerts/scheduler.ts`) runs once per server, so two open tabs
  never fire one alert twice. It checks each symbol with active alerts in turn:
  - Price alerts of one symbol share one quote, at most each `ALERT_MIN_CHECK_SECONDS` (30 s).
    The quote cache is shared with `/api/quotes`; a cached quote costs no call.
  - Indicator alerts of one symbol and timeframe share one bars call, after a bar close.
    After a call with no new closed bar (the market is closed), the wait doubles from one
    bar span (at most 1 h) up to 1 h. A new bar sets the wait back.
  - When the budget is used up, the checker still visits each symbol: expiries and quotes
    in the shared cache cost no call.
  - Upstream calls in any 60 s window stay at or below `ALERT_CALL_BUDGET` (default 150).
    The synthetic provider has no budget.
  - `checkIntervalSeconds` in `GET /api/alerts` is `max(30, symbols / budget × 60)`.
  - State-only changes are saved within 60 s; events and status changes are saved at once.
- The MSW mock (`mocks/alerts.ts`) implements this table. It has no checker; `mockFireAlert`
  fires an alert for tests and pushes a `fired` message to the open streams.
